# T6：Dev 对照、失败定位与冻结

日期：2026-10-20。**工程验收已完成，模型业务效果未达标：B0、B1、B2 各 0/9。** 本报告是固定 retail 环境的本地派生评测，不是官方 τ2-bench 排行榜。9 道不同 Dev 题重复用于三组，共 27 次运行；不是 27 道独立任务。Test 4 道未执行，80 道目标仍未达成。

## 输入、职责与验收口径

`cli evaluate → evaluate_batch → evaluate_episode → RetailRuntime.run_turn` 使用 CLI 相同的模型—工具循环和业务保护层，没有给评测另写一套 Agent。每题创建独立线程，从同一固定原始数据库开始。模型只看到当前用户消息、运行时消息和公开工具 schema；用户脚本只读取开场、用户私有事实与固定回答规则；评分器才读取预期检查项。脚本不读取目标状态来替模型规划，也不把普通文字追问自动转换成工具调用。

`user_script.py` 只响应 `identity / order / cancel_reason / return_items / refund_method` 五个标签和当前展示的提案。确认规则按用户原始意图和提案中的商品、参数判定，不能批准其他目标；撤回取消意图后不能继续批准取消。未登记的字段保留为 `script_unhandled`，不偷偷扩展脚本。

`score_episode` 检查最终业务状态、其他对象和支付副作用、实际确认回执、必要转交，再区分候选答复与任务成功。状态通过的候选还必须复核必要沟通。`answered` 本身不是成功；流畅答复也不能覆盖错误状态或缺失确认。超时、脚本失败和环境异常均留在已分配分母，未知状态单列。

沟通 rubric `t6-v1` 在配置中登记：完整满足用户目标、事实准确、不虚构执行或退款、如实说明部分完成/拒绝/转交。本轮由助手离线辅助语义复核，不声称独立人工标注或全自动语义评分。每组仅 task 24 进入客观通过候选；三次最终复核均失败，因为只追问身份、没有完成保留 grill 后查询两件 T-shirt 材质的完整目标。其余题已有确定性失败，不需要靠语义判断改变结论。两轮预跑的同一候选也分别保留复核记录。

原始 `results.jsonl` 不覆盖；`communication-reviews.json` 绑定原始文件及条目哈希；`reviewed-results.jsonl` 和 `reviewed-report.json` 单独保存。每组分母 9，待复核 0。评分器被故意破坏目标状态或确认信息时，仍必须失败。

## 五题预跑与一次有限取舍

预跑 ID：2、24、48、50、69，B0。初版 5 题共 41.015 秒，每题中位 7.525 秒、P95 11.896 秒；5299 输入 / 205 输出 tokens，0/5 成功，零工具请求。Python 进程峰值 RSS 121,503,744 bytes，抽样 Ollama RSS 最大 437,780,480 bytes。预跑首轮没有取得 loaded-model 指标，保留缺失而非填零。

据此简单线性估算 27 次单请求运行约 221.5 秒；这是短失败路径估算，不是完整业务流程预算。每题仍保留 900 秒上限，27 次的理论串行上限为 6.75 小时；如果触发多轮工具调用，不能使用短失败耗时估计吞吐。

一次 Dev 提示尝试将“补信息必须调用 ask_user”和五字段说明放到 prompt 前部，并强化工具描述。相同五题仍 0/5、零工具请求；5894 输入 / 208 输出 tokens，增加 595 输入 tokens（约 119/题）。第二轮耗时 25.113 秒，受暖缓存和服务状态影响，不能把它写成提示带来的加速。撤回额外提示，用原始 T5 prompt/schema 冻结最终对照；两轮 prompt、schema、原始结果和复核记录均保留。

内存指标不是整机统一内存总量：Python RSS 是该进程峰值，Ollama RSS 只是抽样；后续 `/api/ps` 报告 loaded-model 4,119,016,480 bytes，不能与 RSS 简单相加，也不代表精确 Metal 峰值。最终三组 Python 峰值最大 125,091,840 bytes。没有安装 psutil、PyTorch、Docker 或下载额外模型。

## 原生协议诊断与问题复盘

最终对照后另开两个非 Test 诊断线程，保留实际 HTTP 请求。身份与订单齐全的查询产生 3 次模型请求、2 次原生工具调用（查身份、查订单），得到 pending；身份缺失的查询仅 1 次模型请求、0 次工具调用，返回文字追问。每次 HTTP 请求均携带九个工具 schema。这支持“框架确实发送工具、该模型能原生调用；缺身份时未正确选择交互工具”的定位，不支持“所有 Function Calling 都不可用”。诊断不是新的评测题成功数，不能混进 9 题分母。

没有将 Dev 开场补成身份齐全，没有强制 tool_choice 或替模型接业务链，没有云模型、Mock 或提示式 JSON 回退。上述失败仍开放。当前冻结可支持如实撰写失败报告，不能作为高成功率业务 Agent 的证据。

[真实问题记录](problems.md) 包括：完整快照序列化污染无关字段（已修复且评分不放宽）；缺身份不选 ask_user（未解决）；超范围请求缺转交（未解决）；分母、状态与沟通、schema 口径的工程回归（已修复）。修复仅改适配层差异提交，固定上游方法和原始数据保持不变。

## 沿一条业务流程理解

以取消订单为例：用户输入意图 → 模型请求 `ask_user(identity)` → 运行时返回 `needs_input` → 脚本只回复身份 → 模型查询订单并提出取消 → 应用展示具体 proposal → 用户确认该 proposal → 事务提交业务变化和回执 → 评分器检查订单、支付、其他订单、确认与答复。模型负责选下一步，应用负责是否允许执行，评分器事后判断是否完成。

本轮实际断在第一处：模型用普通文字追问，运行时得到普通结束答复；脚本没有 `needs_input` 就不继续。这能解释“没有异常、代码测试通过，却业务 0/9”。不能因为模型说了句话就伪造一次 ask_user。

工程已实现并验证；用户理解仍待口述，不要求独立修改代码。两个复述点：① schema 合法为什么仍可能业务失败？② 一次允许的重试为什么可能增加成本，却不一定提高整题成功率？
