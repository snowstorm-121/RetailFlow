# 按会话状态筛选模型可见工具

## 假设与实现

假设：在身份、订单状态已知时，减少不适用的工具可能减少模型选择错误。此假设需要真实运行验证；工具数量减少本身不代表业务成功。

新增配置 `state_tool_filter`，默认 `false`，由 `react_agent.tools.retail_tools_for_session` 生成本次请求的工具列表。

| 会话状态 | 模型可见工具 |
| --- | --- |
| 未定位用户 | 两种身份查询、ask_user、转交 |
| 已定位，尚未查询订单 | 用户资料、订单、商品查询，ask_user、转交 |
| 最近查询订单为 pending | 上一行加取消工具 |
| 最近查询订单为 delivered | 上一行加退货工具 |
| 最近查询订单为其他状态 | 只读查询、ask_user、转交 |

每次请求重新读取实际会话状态。查询另一订单可以切换目标；不会读取评分标签，也不根据任务编号决定工具。可见性不是权限：即使工具可见，dispatcher 仍检查身份、所有权、参数和业务政策。例如未定位身份时转交仍可能被原有授权规则拒绝。写操作继续生成提案，确认由应用处理。

协议修复时原有的 ask_user 限制优先。执行层已检查请求工具是否在本轮提供的列表中。上下文预算仍按完整工具集合预留，与基线保持相同的保守预算；这轮不同时调整提示词、预算、模型或用户请求。

## 验证与复现

新增 7 项测试，覆盖未定位、无订单、pending、delivered、cancelled、return requested，以及身份查询和订单查询后实际发给模型的工具列表变化。实现前测试失败，实现后全套 142 项通过。

运行以下开发诊断需要已有本地 Ollama 模型；不会下载模型。输出目录必须不存在，避免覆盖历史结果：

```bash
.venv/bin/python examples/tool_visibility_comparison.py \
  --config configs/local.json --output artifacts/my-tool-visibility-check
```

两个固定、已见用户请求分别在开关关闭与开启时运行。每次使用独立数据库与会话。取消场景只验证生成提案，不提交确认；不能当作完成取消业务。执行结果逐条落盘，失败不会丢弃。

这些单次诊断不能估计稳定成功率，也不是新的 Test 或完整 B0/B1/B2 对照。系统时钟和推理时序仍会变化，因此不是逐字确定的模型输出实验。

## 工程取舍

这个方案把业务状态转成工具选择范围，代价是模型必须先读取目标订单才能看到写工具。它无法修复政策误述、漏答或无关追问，也不能代替写入权限校验。是否默认启用取决于后续完整任务集验证，而不是单例输出更流畅。

技术讨论时可以沿 `load_session → retail_tools_for_session → bind_tools → dispatch_tool` 解释“候选工具筛选”与“执行授权”的不同职责，并说明为何保留只读查询使模型能够切换订单。

## 本地实测结果与决策

| 请求 | 筛选关闭 | 筛选开启 | 目标检查 |
| --- | --- | --- | --- |
| 只查询订单状态 | failed，追问协议失败，4 次模型请求 | needs_input，却追问取消原因，5 次模型请求 | 两者均未准确完成当前查询沟通 |
| 请求生成取消提案 | answered，3 次模型请求 | answered，3 次模型请求 | 两者均只输出普通 action JSON，没有原生写工具调用或提案 |

四次运行均未达到各自诊断目标，业务快照前后哈希均一致。普通 JSON 文本不作为 Function Calling，也没有被程序解析后自动执行。`answered` 仅表示模型结束答复，并不代表动作完成；这一点仍须业务末态与提案检查验证。

[汇总](evidence/tool-visibility-20261104/summary.json)及同目录完整轨迹保留全部失败。未观察到本次筛选带来的任务收益，因此保持默认关闭。不要将更规范的暂停状态视为成功率提升。后续应先研究文字动作声明与原生调用之间的协议偏差，并避免为单个样例继续盲目改提示词。
