# 业务链路复查与改进

本次基于 `95aad9c` 检查 CLI、模型工具循环、业务执行与持久化边界，并运行完整工程回归。范围是现有订单场景，不扩展服务、模型或业务类型。

## 修复一：预算耗尽的退出码

CLI 原先只把 `failed` 转为退出码 1；`budget_exceeded` 在单条消息模式下会返回 0。调用脚本因此可能把停止执行当成正常结束。

现在两者均返回 1，并继续输出原始状态与轨迹路径。测试先复现旧行为返回 0，再验证修复。退出码只反映运行状态，任务是否成功仍须检查业务末态和必要沟通；退出码 0 也不意味着业务目标已实现。

## 修复二：提案声明的词序变化

旧逻辑能识别 `A return request has been created for the headphones.`，却漏过 `A return request for the headphones has been created.` 和 `... was submitted.`。此时模型没有调用写工具，图仍可能返回 `answered`。

修复允许商品说明出现在请求与完成谓语之间，仍要求模型通过原生工具创建提案，最多使用既有的一次协议反馈。回归检查不仅验证进入 `needs_confirmation`，也验证订单仍是 `delivered`，未在用户确认前执行。否定句及条件句另有反例检查，避免把 `has not been created` 或 `can be created after confirmation` 当成已完成声明。

这只是针对已知英文表达的有限检测，不是通用事实验证器。写权限来自应用侧提案和确认；文本检测不会生成业务操作，也不能保证识别所有虚假陈述。

## 技术讨论的证据入口

- **授权边界**：为什么用户说“同意”还必须绑定具体 proposal_id、订单与参数？见 `environment.py` 和确认变更示例。
- **事务与重放**：如果订单写入成功但模型回复超时，如何避免重复退款？见 `storage.py`、执行回执和相关回归测试；当前保证仅限本地事务边界。
- **故障传播**：CLI 显示错误而退出码成功会怎样影响调用者？本次预算退出码修复提供可复现反例。
- **模型与应用分工**：模型声称创建提案时，实际数据库为何没有变化？本次两种词序测试展示文本、工具调用和业务状态之间的区别。
- **上下文取舍**：用户目标、完整工具消息对和输入预算冲突时保留什么？见 `context.py`；必需内容超预算时明确停止。

这些材料证明代码实现和验证过程，不代表使用者已经能独立解释或修改。准备技术讨论时，应先自行画出一次取消订单的数据流，再用代码检查自己的解释。
