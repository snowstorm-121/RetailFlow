# 按顺序整理事实的原生提案恢复

## 问题与实现

此前已确认：模型拿到了订单、商品和原支付方式，却以普通文字声称已创建提案。移除示例或助手草稿均未解决该输入。此次将恢复限定为独立一步，而不是从模型文本 JSON 提取参数执行。

`isolated_proposal_repair` 默认关闭，只在已有 proposal 协议恢复阶段启用。输入保留原业务政策，将当前可见的用户原话、原生工具请求和真实工具结果按时间顺序打包；不包含没有工具调用的助手草稿。工具仍为原来的集合，模型自行选择工具和参数。恢复仍计入原有一次 dialogue repair 及模型调用预算；纯文字不能把恢复标成 answered，返回 proposal_not_created。工具校验、身份、所有权、政策、确认及事务机制保持原样。

最初将用户消息和工具结果分组的诊断产生了重复退款方式追问，未通过。按原顺序打包后，真实模型正确调用 return_delivered_order_items，选择四件非咖啡机商品和原信用卡。两份诊断及 HTTP 输出均保留，不能只展示成功样例。

这一方案不是通用状态规划器：恢复输入来自既有上下文裁剪结果，不保证覆盖已裁掉的事实；当前也没有将图外 application_result 消息打包为事件。因此复杂多订单、已提交操作之后的恢复仍有局限，保持默认关闭，不宣称已解决全部状态管理问题。

## 验收与测试

新增测试先复现输入仍混有草稿、恢复文字被标记为完成，再实现最小修改。检查真实提案路径仍等待确认、业务尚未写入、完整审计历史保留、用户后续更正顺序不变、恢复不得突破原调用预算。

全套工程测试 **167 passed**。模型实验不是 Mock；确定性回归中的模型替身仅验证应用行为，不能代替原生调用实测。
