# 取消目标登记与完成检查

## 范围

本轮落实“目标登记—完成证据—终止条件”，但仅覆盖明确的“全部待处理订单”或直接给出订单编号的取消请求。它不是通用规划器，不能用于按商品描述解析取消范围、退货或任意查询。新增 cancel_goal_tracking 默认关闭，CLI 实验入口为 configs/cancel-goals-local.json。

模型通过原生 update_cancel_goal 登记 scope、order_ids、source_quote。程序检查结构、完整订单号和引用来源，但引用正确不等于语义解释正确；每条新用户消息都重新核对目标，确认事件沿用已有目标。模型若错误登记 none 或旧范围，仍可能漏任务，因此不能声称此层完整解决自然语言目标识别。

目标复用 SQLite runtime_state 元数据保存，不新增服务。全部待处理订单在身份确认和成功读取用户清单后，从本人订单的当前状态冻结。该操作只建立目标，不执行取消，也不授予确认权限。

完成条件为实际订单状态 cancelled 且同一会话有成功取消回执；取消目标保留到完成，不因一笔提交就自动消失。模型提前结束时，在原恢复次数和调用预算内尝试原生恢复，仍未完成则明确失败。缺少取消原因等信息时保留 ask_user 路径。取消提案不得超出已登记范围，每笔仍独立确认。

## 验证过程

原生登记烟测中，“全部取消”“补充原因”“撤销取消”“缩小到指定订单”四种输入正确。退货反例错误返回 selected + 空列表，已作为失败保留；运行时拒绝这种非法计划，不进入业务链路。

先写失败测试，再实现和修复。测试覆盖：

- 非法/空计划、伪造引用、订单号前缀误匹配。
- 未取得身份或清单时不能宣布目标完成。
- 仅订单状态改变但没有成功回执不算完成；他人订单不可泄露状态。
- 重启恢复后继续剩余订单，每笔独立确认。
- 用户改为保留订单时刷新目标，旧提案失效。
- none 目标或范围外请求不能创建取消提案。
- 未完成目标仍允许缺参追问，不应被强行导向写操作。

最终完整工程测试 **181 passed**。测试替身仅验证应用行为；下述业务试验使用真实本地模型。

最终版共 14 次模型调用、14 次工具调用（含目标登记、提交及一次读重试），未突破预算。真实生成两个不同 proposal_id，并分别收到确认：

- #W5056519：取消原因 ordered by mistake；信用卡退款记录 $243.62。
- #W5995614：取消原因 ordered by mistake；信用卡退款记录 $1,074.31。

只读 SQLite 重查三组末态哈希：基线和初版未改变订单；最终版仅这两笔订单改变，用户与商品数据不变，成功取消回执恰好两条。最终回复列出两笔取消及金额，说明 5–7 个工作日退款，没有声称已经到账。

沟通复核沿用 t6-v1，由 Codex 辅助离线复核，非独立人工评审；绑定原始结果文件哈希。最终结果见 [reviewed-result.json](evidence/cancel-goals-20261116/goals-final/reviewed-result.json)，独立状态审计见 [audit.json](evidence/cancel-goals-20261116/audit.json)。各版本 manifest 的源码哈希已核对。

## 独立审查后的边界修复

审查发现，同一范围在补充原因后重新登记时，旧实现会重算 targets，可能丢掉状态已改变但没有回执的原目标。新增回归先在临时测试数据库复现，再修改为：scope 和 order_ids 未变则保留冻结集合；真正更改范围或撤销时才重建。复核该修复的目标专项测试 14 项通过，全套 181 项通过。

上述模型试验使用修复前的 source-final 快照；交付代码另保存在 source-reviewed。审查后的修复由确定性回归验证，未再次运行模型任务，不把不同版本的源码哈希混为一谈。

## 统计与结论边界

新增工具计数器认识 update_cancel_goal：引用和结构有效才计为合法调用，非法计划仍不计合法。这只是扩展合法协议计数，不修改任务状态、确认、副作用或沟通判定；目标登记本身不计任务完成。

本轮只有一题定向最终成功，未重复多次，也没有运行完整 Dev 或 Test。**不能把本轮结果拼接为 4/9**。最近完整 Dev 仍为上一轮 proposal-recovery 版本的 3/9。新目标模式不适用于全部任务，不能默认为通用入口。

已实现的是有限取消目标账本和执行约束，不是“用户已经理解”或“能独立修改”的证明。基础数据流是：模型登记目标，程序记录未完成项，模型提出下一步，用户确认，程序以真实回执判定完成。

下一步应先验证更多取消范围变更与重复运行，评估目标登记稳定性，再考虑将目标类型扩展到退货和查询。不能仅因为这一题通过就把新机制推广到所有业务。
