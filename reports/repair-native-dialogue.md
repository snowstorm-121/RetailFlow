# 原生工具调用与多轮业务修复

日期：2026-10-21。**当前 V5 完整 Dev 1/9，V4 2/9，效果仍未稳定；129 项工程测试通过。** 原生链路已进入真实业务，但不宣称问题彻底解决。修复在 `fix-native-tool-dialogue` 分支开展，基于原交付提交 `b23f70e`。T6/T7 的零成功率、冻结清单、数据与报告均保留。本记录是已见 Dev 上的开发排障，不是新的未见集成绩。

## 验收与边界

使用原有 Ollama 0.15.6 和固定 digest 的 `qwen3:4b-instruct-2507-q4_K_M`，无下载、安装、云 API、模型训练或共享服务改动。仍采用原生 `ChatOllama.bind_tools`；没有把普通文字转换成伪造工具调用，也没有使用提示式 JSON 工具协议。

验收分开记录：工程回归、真实缺信息业务流程、完整 Dev 的最终状态/确认/副作用和沟通复核。测试通过、工具 schema 合法、已产生提案或已经写入正确订单，均不能单独代替整题成功。

## 根因与修复

1. **工具契约不完整。** `ask_user.fields` 原先只是任意字符串列表，而脚本只认识五类字段。现在 schema 和执行校验同时限制 `identity / order / cancel_reason / return_items / refund_method`，拒绝空列表、重复字段和未支持字段。
2. **普通文字追问被当作结束答复。** 识别常见英文缺信息请求后，一次用户事件最多注入一次协议反馈，在同一模型调用预算内要求模型重新生成真实原生调用。初始身份追问保留完整上下文；已经定位用户后的补信息重试只引用失败请求，避免模型延续错误的普通答复。短引用明确标记、仅进入模型输入审计，不冒充真实用户事件或进入身份依据。重试没有原生调用就失败，不能用一句结束语冒充完成。
3. **模型编造了可命中的示例身份。** 查询身份前，参数必须能在实际用户消息中找到；通用示例没有姓名、邮箱、订单或期望答案，且不会持久化为用户消息。这只是模拟环境的字面来源校验，不是生产账户认证。
4. **把允许的原生调用误当协议错误。** Ollama 原生响应允许说明文字与单个 `tool_calls` 同时出现。现在执行单个真实调用，说明文字仅保留审计；多调用仍拒绝，说明文字不会成为写入确认。
5. **用文字确认替代创建提案。** 有已核实目标订单时，明确的“是否继续这次取消/退货”会触发一次业务协议反馈；模型仍需自己选择工具和参数。字段追问与操作确认分别处理。应用始终要求具体 `proposal_id`，未确认订单不能变化。
6. **过期反馈污染后续上下文。** 完整历史保留，但旧协议反馈在下一次调用后退出模型视图。实际提供的工具名和完整模型输入逐次记录；模型请求未提供的工具时不派发业务执行。
7. **长业务路径预算不足。** V2 的任务 48 已连续读取三个订单并找到目标，但在第六次模型请求后停止。V3 单轮上限明确从 6 改为 12，每题仍最多 24 次模型请求、10 个用户事件、900 秒。合成的重试输入也重新检查上下文预算。此变化意味着不能宣称与历史运行预算相同。
8. **政策提示易混淆。** 改为明确的 CANCEL / RETURN 正向规则：pending 可取消、delivered 可退；客户不知道订单号时可检索已列出的订单；缺少原因须追问。模型仍可能违反提示，评分器不会迁就。

模型输入包含两个不含业务事实的原生追问示例，标记为 `protocol_example`。它们的工具返回是提示示例，不计为实际执行或实际用户回答；真实轨迹与计数只来自运行时调用。

V4 在上述修复后进一步补齐真实执行摘要：取消退款的金额、支付方式和时效来自已提交订单的退款记录与支付类型；退货摘要明确实际商品、`return requested`、退款未结算、不能再次退同单，以及模拟邮件说明。没有按模型文字生成退款事实，也没有声称发出真实邮件。提示补齐固定政策中的一次退货限制、后续说明与逐项答复要求。上下文预算拒绝时不再错误增加 episode 模型次数；“Would you like me to return/cancel…” 也不能绕过提案要求。新增回归均先复现失败再修复，全项目 126 项通过。

当前固定数据库的 pending 订单均只有一笔 payment；这些结果不能证明多支付或混合旧退款状态。未来若扩展到该状态，需要将本次新增退款与历史退款分开，当前未扩展工具或数据范围。

V5 进一步修复已由真实 V4 轨迹证实的上下文缺陷：工具消息变多后，最初的 T-shirt 查询目标被裁掉，最终仅保留补身份、退款方式及确认。现在有界会话的全部用户要求和更正按原顺序进入必保留块，超预算时明确停止，不静默忘记用户目标；旧的“40 轮用户消息只留最新”测试同步改为超预算拒绝。退货执行摘要保留实际商品名与 ID 配对，便于裁剪后的准确复述；这不表示 V4 实际配对错误，V4 的 Vacuum/Headphones ID 本身正确。另将实际观察到的“return request has been created”无工具结果声明纳入一次原生提案重试；仍不把文字声明变成执行。129 项工程回归通过。

## 用户脚本的独立修正

V1 保留原脚本。V2/V3 通过配置中可审计的 `user_script_overrides` 修改用户侧回复，只在对应字段被原生请求后提供，不预先进入模型上下文。

| 任务 | 已核实问题 | 新版本处理 |
| --- | --- | --- |
| 24 | 上游允许用户编造取消原因，派生脚本却没有登记原因回复 | 固定回复 “I ordered it by mistake.”，保留随后的拒绝取消、改问 T-shirt 规则 |
| 48 / 69 | 上游身份说明为用户名串，与新增的姓名字面来源检查不兼容 | 由固定源数据库核验姓名和 ZIP，明确登记 Daiki Johnson / Emma Smith 的身份回复 |
| 73 | 用户说 coffee machine，唯一对应商品实际叫 Espresso Machine；精确 consent 排除项错配 | 排除项改为 Espresso Machine，预期退货商品 ID 不变 |
| 113 | 模型未问原因就猜 no longer needed，被用户拒绝 | 不改脚本或 consent；仍要求被问后才回复 ordered by mistake |

`user_view` 只允许覆盖五种用户回复字段，仍排除 `expected_checks`。没有从评分标签反推用户回答或给 Agent 提供正确订单/商品 ID。脚本缺陷与模型缺陷分开记录，不能用前者解释全部零分。

## 最小数据流说明

输入是用户业务意图；模型输出是普通文本或带名称/参数的原生 `tool_calls`。图只派发实际调用，工具结果再交回模型。`ask_user` 使运行时暂停；写工具先产生提案，只有应用收到该提案的明确确认才提交业务事务。执行结果再作为受信应用事件交给模型复述；评分器独立查末态与必要沟通。该阶段代码工作由 AI 助手辅助完成；真实取消单例仅验证对应执行路径，不构成普遍业务可靠性或独立编码能力的证明。
