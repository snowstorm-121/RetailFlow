# 身份追问修复与提案声明检查

## 本轮目标

沿用已有 4B、原生 Function Calling、固定 Dev 与原评分，定位 Dev73 在身份追问阶段停止的问题。没有下载模型、使用云推理、修改用户脚本或运行 Test。Cloud 上报在本轮对照中关闭，避免引入网络耗时差异。

验收分两层：真实 ask_user 调用能否恢复交互，以及完整业务状态、确认和沟通是否通过。前者不能替代后者。

## 诊断与单变量实验

原始失败输入两次输出普通身份问题，没有原生调用。仅套用已有聚焦追问提示、保留协议示例，仍然失败；移除示例后产生原生 ask_user。另一个明确点名身份信息的最小提示也可产生原生调用，但改变了输入，不能作为完整任务收益证据。

新增 `isolated_information_repair`，默认 false。开启时，已有的一次追问恢复只保留系统指令和引用的失败问题，不附带示例，也不要求先获得 user_id。它仍由模型生成原生调用，参数经过原校验；不解析文字为执行指令，不增加原恢复次数或模型调用预算。普通业务轮次、政策、工具权限和确认流程不变。

这验证的是组合方案“身份阶段也聚焦 + 恢复时去掉示例”，不能把完整任务差异全部归因于某一个因素。引用模型问题也可能继承其错误需求：此次模型将“邮箱或姓名和 ZIP”改写为“姓名和邮箱”，因此不能宣称语义完全保持。

## Dev73 配对结果

两组均从独立初态开始，使用 configs/return-receipt.json 的原设置、B2 和同一任务，仅切换上述开关。

| 条件 | 身份追问 | 最终结果 | 模型调用 |
| --- | --- | --- | --- |
| 基线 | 两次文字追问，没有原生调用 | failed / information_request_not_structured；0/1 | 2 |
| 实验 | 原生 ask_user 成功；随后完成身份、资料和订单查询，并追问退款方式 | answered / missing_confirmation；0/1 | 9 |

实验组没有调用退货工具，也没有真实提案。模型最终声称已创建退货请求并承诺 3–5 日退款，实际业务状态未改变，状态评分包含 missing_confirmation 和 target_state_mismatch。保留该失败，不做沟通复核来覆盖客观失败。

两组 SQLite 末态哈希与结果文件一致，且业务状态均与初态一致。没有完整 Dev 新成绩，历史回执实验的 2/9 仍只属于历史版本，不能移作本轮结果。本轮没有显示端到端收益，因此不开启默认配置、不追加全量评测。

## 随后修复的错误反馈漏洞

原检测器能识别“return request has been created”，却漏掉恢复后输出的“return request has been successfully created”，导致运行时以 answered 结束，评测再依据真实状态判失败。

回归测试先复现 answered，再扩展原模式匹配可选的 successfully；恢复机会用完后，这类声明返回 failed / proposal_not_created。测试同时检查无提案、业务状态不变和仅一次恢复。既有否定句反例仍通过。这是已观察到的表达覆盖修复，不是通用幻觉识别，也不是业务成功率提升。

最终工程测试：163 passed。追问实验另覆盖缺身份时输入隔离、预算不足退出、恢复仍输出文字时失败。没有为了验证此检测器再次运行完整模型任务；上表保存的是检测器修复前的真实结果。
