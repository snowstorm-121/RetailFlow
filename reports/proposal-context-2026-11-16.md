# 退货提案失败的上下文对照

## 输入与边界

使用上一轮 Dev73 失败轨迹的最后一次提案恢复输入，保留业务政策、用户原话、订单商品及支付信息。用户在本机执行诊断脚本，模型仍为已有 qwen3:4b-instruct-2507-q4_K_M，temperature=0、seed=42、num_ctx=8192、num_predict=768，三组均提供同样的九个工具。

本轮只观察模型输出，不执行返回的业务工具，不运行完整任务或 Test。每组一次，不构成稳定性估计。输入来自已见开发任务，不能解释为未见任务成绩。

## 结果

| 条件 | 实际输出 | 原生调用 |
| --- | --- | --- |
| 原始上下文 | 声称退货请求已成功创建，承诺 3–5 日退款 | 0 |
| 移除协议示例 | 普通文本 JSON 冒充成功工具回执，包含正确的四个商品 ID 和原支付方式 | 0 |
| 移除无工具调用的助手草稿 | 正确列出四件商品并排除咖啡机，但声称请求已暂存，承诺 5–7 日退款 | 0 |

三组 HTTP 均为 200、done_reason=stop，原始 message 均无 tool_calls；框架解析文本与原始文本逐字一致。未发现框架丢失调用，也不是输出预算截断。没有将任何文本 JSON 转换为调用或真实回执。

这次观察说明模型在这个输入中能够选出所需商品和支付方式，却没有使用原生执行通道。它否定了“仅删掉示例或助手草稿即可恢复此步骤”的当前方案，不能据此断言模型始终无法调用工具，或已经证明唯一根因。

## 决策

不修改默认上下文代码，不追加完整 Dev，不上调验收指标。此前 2/9 仍仅属于历史回执版本，本轮三次诊断不能替代端到端结果。

后续应先讨论一个有限的执行阶段：保留原 ReAct 主循环，只在检测到没有真实提案的执行声明后，将用户原始要求与真实工具事实交给一次单独的原生调用恢复。模型仍选择工具和参数，程序不能从这次编造的 JSON 提取参数执行。恢复应计入原调用预算，并沿用身份、政策、用户确认和重复执行保护。

这比单纯修改提示词更明确地改变了执行结构，应单独登记和对照；过去通用工具筛选未显示收益，不能直接复用它并宣称问题已解决。实施前需明确缺参、目标变更、多订单和无关答复的边界。若此路线仍无法稳定产生正确原生调用，应停止围绕同一输入反复搜索提示词，重新讨论模型与架构约束。

[原始 HTTP、解析结果、脚本与校验摘要](evidence/proposal-context-20261116/summary.json)均保留。诊断脚本只读固定失败输入，输出存放在 artifacts 中，没有导入业务执行入口。
