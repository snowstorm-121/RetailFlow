# RetailFlow 真实问题记录

记录日期：2026-10-20。下面分别标明真实模型观察和工程回归发现。保留失败证据；不把未解决的问题写成优化成果。

## P1：提交完整模型快照会修改无关订单的 JSON 形状

场景：T6 评分器首次执行真实上游取消方法，目标订单已取消，却收到 `other_order_side_effect / target_extra_change`。原始 DB 和写后业务快照逐对象比较，1000 个订单均出现差异。

原因证据：`RetailDB.model_validate` 为缺失可选字段补默认值，原先的 `completed.model_dump_json()` 把它们全部写回。这是适配层的快照提交问题，不是上游取消政策执行错误。旧 T3/T5 的支付次数和目标状态测试未覆盖完整无关对象的字段形状。

改动：`environment.py` 用执行前后规范化模型的差异合并原始快照，保持未发生变化的原始字段。实际业务方法产生的差异仍会被提交并接受评分，未在评分器中忽略差异来放宽通过条件。原始数据和上游业务方法均未改写。

验证：`test_scorer_rejects_wrong_state_and_missing_confirmation_even_with_fluent_answer` 先失败后通过；三组相同保护路径的取消集成测试、原有礼品卡退款及回执重放测试通过。评分器故意破坏目标状态或去掉确认后仍判失败。

限制：未清洗或覆盖旧本地会话。评测每题从固定原始 DB 新建线程；历史 T5 轨迹保留原状，不能把 T6 修复追溯成旧版本已具备的保证。

## P2：缺身份时模型用文字追问，未调用 ask_user

场景：B0 五题预跑中，模型回答“请提供邮箱或姓名和 ZIP”，却没有任何原生工具调用。运行时因此按普通答复结束；脚本没有收到 needs_input，不会私自把答案补给模型。

日志：`artifacts/t6/pilot-v1/results.jsonl` 及对应 `traces/`。五题共 41.015 秒、5299 输入 tokens、205 输出 tokens；全部没有工具请求，三个写目标未完成。task 24 的最终问题也没有提供所需的两件 T-shirt 材质。

定位：同一已有模型在 T4/T5 已实际发出原生工具调用，本次实际模型输入仍绑定同九个 schema，因此不能把它描述为“Function Calling 协议完全不可用”。这是特定输入和上下文下的模型决策失败；原生调用能成功并不等于缺信息时必然选 ask_user。

尝试与复测：在 prompt 前部强化“追问必须用 ask_user”和五个字段标签，并补工具说明；相同五题 B0 复测仍无工具调用。第二轮 25.113 秒、5894 输入 tokens、208 输出 tokens。耗时差异受缓存/服务状态影响，不能单凭这两轮宣称加速；输入增加 595 tokens，没有观察到任务收益。

取舍：撤回额外提示，保留两轮 prompt/schema 快照及结果，用原提示完成最终对照。未转换文本为伪工具调用，未强制业务链，未扩大脚本兼容字段或把隐藏用户事实直接放进开场消息。

限制：仅有一轮有限尝试，没有声称找到最佳提示。最终对照保留这类失败。

## P3：模型文字拒绝超范围请求，未执行要求的人工转交标记

场景：Dev task 50 要求撤销已经取消的订单。五题预跑与复测中，模型均直接文字拒绝或要求新信息，没有 `transfer_to_human_agents` 成功记录。业务未被错误改写，但这不满足冻结任务的完整目标。

证据：两轮结果均为 `transfer_mismatch`；不能因为回答听上去合理，或因为没有副作用，就计为任务成功。这里的转交只是本地标记，不存在联系真实客服的行为。

处理与复测：评分器同时检查状态、副作用和实际转交证据；相同五题第二轮仍失败。没有另加一个按任务 ID 自动调用转交的分支；该模型选择问题保持开放，纳入最终结果和分母。

限制：没有证据表明上下文或重试能修好这类没有进入工具链的失败；最终比较不能凭空归因。

## P4：成功口径、异常分母与 schema 合法率容易混淆

工程复核发现：批级异常回退一度丢失“该题是写任务”的静态分类；状态修改指标一度错误沿用了端到端成功；订单 ID 只检查字符串类型会把缺 `#` 的调用错记为 schema 合法；无法确认的故障触发状态不应伪填 0。

修复：异常保留静态任务分类；状态/确认/政策结果与语义沟通结果分开；合法率纳入已发布 schema 的订单 ID 格式；未知的故障、状态及违规检查结果显式单列。普通 `answered` 只表示模型产生了结束答复。

验证：`tests/test_evaluation.py` 中的超时分母、批级异常、状态成功但沟通失败、订单格式及三组一致保护路径测试。该项是可复现的工程回归发现，不冒称真实 Dev 中已经发生过服务崩溃或高并发事故。

语义复核采用预登记 rubric，由助手离线辅助检查完整请求、最终答复与业务事实，保留原始机器结果和单独的复核决策。它不能覆盖失败的业务状态、确认或副作用检查；也不冒称独立人工标注或全自动语义评分。

## P2 补充定位证据

最终三组各 9 道 Dev 均未进入工具链。另开非 Test 的原生协议诊断：身份齐全时 3 次模型请求、2 次原生工具调用；身份缺失时 1 次请求、0 次工具调用。实际 HTTP 请求每次均携带九个工具 schema。证据在 `reports/evidence/t6/diagnostics/`，轨迹映射见 `trace-index.json`。这排除了“框架根本没有传工具”的解释，但不能把两个诊断视为九题评测的补考或增加成功数。问题仍未解决。

## P5：Test 中 schema 合法但身份编造、协议错误

三组 task 68 各有两个参数形状合法的原生工具请求，模型却自行编造 Jane Doe 邮箱/姓名/ZIP，并把说明文字与工具调用混发。既有协议保护在执行前两次返回 PROTOCOL_ERROR；最终仅追问身份，没有给出应查到的 $829.43。每组 task 51 另有一次身份定位前读订单请求，被 AUTH_REQUIRED 拦截。保护拒绝是真实发生的，不等于任务完成。

定位与证据：见 T7 全部实际轨迹、`reports/evidence/t7/*/trace-audit.json` 及 `reports/t7-test.md`。每组三个参数/schema 合法请求全部被拦，成功 0/4，所有业务状态不变。`first_observed_error` 只记录 dispatcher attempt，因此 task 68 虽为 null，ToolMessage 仍记录两次协议错误，报告明确区分。

本轮不修改冻结后的 prompt、运行逻辑或评分器；未把幻觉身份补成真实身份，也没有删掉协议规则来提高成功数。问题保持开放。任何后续修复需另建版本，不能再声称当前四道 Test 未见。

## T8 复核：单例演示与正式失败不能混为一谈

T8 使用身份、订单和取消原因齐全的开场，同一已有本地模型经真实工具生成提案，跨 CLI 进程确认后订单 cancelled、支付记录 1→2，完整末态检查通过；另一个 delivered 订单查询后按政策解释不能取消，业务快照未变。实际轨迹与结果在 `reports/evidence/t8/`。这些输入和目标与缺身份的冻结任务不同，不据此修订 Dev/Test 零成功率。

只改 reason 的演示是助手直接调用真实业务保护层，证明旧 proposal_id 被拒绝、新提案须重新确认；没有模型推理，不能说成“模型已学会理解所有需求变更”。T8 未改运行源码、配置或评分规则，未重跑 Test，也没有用新演示替换旧失败。模型选择和交互协议问题保持开放。
