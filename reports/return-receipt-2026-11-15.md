# 从真实回执生成退货说明

## 改动与限制

本实验针对已验证的失败：退货写入正确，模型却虚构退款日期或错误说明再次退货资格。

`return_receipt_response` 默认关闭。开启后，仅在本轮已有成功提交的退货回执、模型循环正常结束为 answered 时，用应用生成的回执说明替换末轮文本。内容来自实际 order_id、return_items、商品名称、退款方式和固定业务政策。剩余商品逐项列出，并说明同一订单不能再次退货或修改。本地不发送真实邮件，也没有可承诺的退款到账日期。

它不改变模型规划、工具执行、用户确认或错误状态；失败及超时不会被自动改成成功。原始模型答复仍在消息轨迹和 original_model_answer 中，应用生成文本另外标记，便于审计。没有新增模型调用，也没有解析文字 JSON 执行业务。

这是一种有限范围的确定性答复方案：它能回答同一退货订单内的剩余商品资格，但会覆盖模型末轮的其他查询答复。不能把它当作通用多目标任务解决方案。涉及其他商品查询、其他订单或未完成动作时仍按原要求评分，缺失必要沟通就判失败，因此暂不启用为默认。

## 验证

新增回归先复现模型错误答复，再验证用户可见文本来自真实回执、原始错误文本保留、调用数量未增加、最终消息与显示文本一致。全套工程测试 150 项通过。

完整 Dev 使用 configs/return-receipt.json，源自 repair-v5 配置，只开启回执输出并记录实验说明；模型、脚本、预算、B2、任务和评分沿用既有设置。两项先前无收益实验（工具筛选和模型答复复核）均关闭。各题独立初始状态，保留所有失败，未运行 Test。

运行命令：

```bash
.venv/bin/python -m retailflow.cli evaluate --split dev --variant B2 \
  --config configs/return-receipt.json --output artifacts/my-return-receipt-dev
```

这是已见 Dev 开发结果，与历史单次运行的差值不等于严格配对的因果收益。实际文本由应用生成的部分应明确归属于工程输出，不能声称模型自身的政策理解提高。

## 完整 Dev 结果

沟通复核后的端到端结果为 **2/9**，通过题为 48 和 69；写任务状态及确认 **2/7**；待复核 **0**。对照此前 11 月 14 日完整批次的 1/9，本次多通过一题，但不是随机重复或同批次配对实验，不能解释为稳定的总体提升幅度。

48 的实际空气净化器退货、原始 PayPal 退款方式和确认均正确。应用生成说明没有承诺到账日期，并准确回答同一订单中剩余吸尘器不能再次退货的问题。69 的笔记本取消与礼品卡即时退款保持正确。24 的 T 恤查询仍漏答，其他题仍存在提案、确认、转交或追问失败。

全部九题只读重查 SQLite，末态哈希与原评分一致。48 只改变目标订单且未实际结算退款；69 礼品卡余额 $62.00 → $2736.40，与 $2674.40 退款相符。仍使用原 t6-v1 沟通 rubric，辅助离线复核绑定原始结果行哈希，不冒称独立人工评审。

最终指标见 [reviewed-report.json](evidence/return-receipt-20261115/dev-B2/reviewed-report.json)。原始 report.json 的 0/9 是三个候选尚待沟通复核时的中间值，两份报告均保留。完整轨迹保留原模型草稿和应用输出，源代码及配置快照按 manifest 哈希校验。

## 决策

保留为显式实验配置，不默认覆盖一般多目标答复。单独运行 `configs/return-receipt.json` 可复现此方案；常规 CLI 配置仍保持原行为。下一优先问题是跨订单检索遗漏与未生成真实提案，当前回执输出不解决这些问题。
