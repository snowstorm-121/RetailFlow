# 商品数量事实与提案恢复

`configs/catalog-facts.json` 是在 scoped-cancel-goals 配置上开启 `catalog_availability_facts` 的实验入口，默认 CLI 不启用。

成功的原生 `get_product_details` 返回产品及全部 variants 后，应用计算其中 `available is True` 的款式数，记为 `available_variant_count`。该字段保留在模型上下文白名单中。数量不表示仓库库存件数，不等于全部变体数，也不来自用户历史购买件数。

当 `return_receipt_response` 根据真实退货回执生成最终说明时，开启该开关会附上本会话各商品最后一次成功查询的名称、ID 和可售款式数。相同产品取最后成功结果，后续失败不会覆盖它；文字明确标记 Last successful catalog lookups，不保证实时库存。不读取当前工具之外的产品数据、不猜测未查询产品，也不保留任意未经核验的模型答案。

因此，这只能保护已经取得的目录数量事实，不能保证模型主动执行查询，不能解决所有附加问题，也不能把部分完成变成任务成功。

另修复原 `isolated_proposal_repair`：恢复模式在当前 graph/run_turn 内持续，允许原生读取所需数据后继续恢复，不因最近一条消息从协议反馈变成工具结果而丢失隔离输入。它仍只在已有提案协议反馈后激活，仍消耗原模型预算，不增加修复次数。原生追问、提案、拒绝、失败或预算耗尽都会结束本轮；下一轮新建 graph，恢复状态不继承。恢复中的纯文本不能冒充提案。

实验中还尝试过在退货确认后重复含问号的用户消息，但真实单题仍漏答且该提醒没有跟踪撤销/已回答状态，因此已撤回，未作为交付功能。
